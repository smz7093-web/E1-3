# Mini NPU Simulator (E1-3)

MAC(Multiply-Accumulate) 연산으로 입력 패턴이 **Cross(십자가)** 와 **X** 중 어느 필터에 더 가까운지 판정하는 Python 콘솔 프로그램입니다.
외부 라이브러리 없이 표준 라이브러리(`json`, `time`, `os`, `sys`)만 사용합니다.

---

## 1. 실행 방법

### 환경
- Python 3.8 이상 (개발·검증: Python 3.14)
- 외부 패키지 설치 불필요

```
E1-3/
├── main.py      # 메인 실행 파일

```

```bash
python main.py
```
실행하면 모드를 고르는 화면이 나옵니다. 1과 2 이외의 값을 넣으면 다시 묻습니다.

```
=== Mini NPU Simulator ===

[모드 선택]
1. 사용자 입력 (3x3)
2. data.json 분석
선택:
```

| 모드 | 동작 |

| **2. data.json 분석** | 필터 로드 → 패턴별 MAC/판정/PASS·FAIL → 성능 분석(3·5·13·25) → 결과 요약(총/통과/실패 + 실패 목록) |

모드 1은 한 줄에 숫자 3개를 공백으로 구분해 3줄씩 입력합니다.

## 2. 구현 요약

### 2-1. 데이터 구조 — `Matrix`
- N×N 값을 리스트의 리스트(`data[r][c]`)로 저장하고, `get(r, c)` / `set(r, c, v)`로 특정 위치 값을 읽고 씁니다.
- `Matrix.from_rows()`는 JSON에서 읽은 배열을 검증합니다. 비어 있음, 행/열 수 불일치, 숫자가 아닌 값이면 `ValueError`를 냅니다.
- 3×3, 5×5, 13×13, 25×25를 포함해 임의의 N×N을 처리합니다.

### 2-2. MAC 연산 — `mac(pattern, filter)`
```python
total = 0.0
for i in range(n):
    for j in range(n):
        total += pattern.get(i, j) * filter.get(i, j)
```
- NumPy나 `sum()` 없이 이중 반복문으로 직접 곱하고 누적합니다. 곱셈과 덧셈은 각각 N²회입니다.
- 패턴과 필터 크기가 다르면 계산하지 않고 `ValueError`를 냅니다.

### 2-3. 라벨 정규화 — `normalize_label(raw)`
data.json에는 같은 의미의 라벨이 여러 표기로 섞여 있습니다. 그래서 입력되는 즉시 **표준 라벨 2개(`Cross`, `X`)** 로 바꾸고, 프로그램 내부의 출력과 비교는 모두 표준 라벨로 합니다.

| 출처 | 원본 | 표준 라벨 |
|---|---|---|
| `expected` 값 | `'+'` | `Cross` |
| `expected` 값 | `'x'` | `X` |
| 필터 키 | `'cross'` | `Cross` |
| 필터 키 | `'x'` | `X` |

- 앞뒤 공백과 대소문자를 정리한 뒤 매핑합니다(`'X'`, `' Cross '`도 처리).
- 매핑에 없는 라벨(예: `'o'`)은 해당 케이스를 FAIL로 처리하고 원인을 남깁니다.

### 2-4. 점수 비교(동점) 정책 — `judge()`
```python
if abs(score_a - score_b) < 1e-9:   # EPSILON
    → 동점: 모드 1은 "판정 불가", 모드 2는 "UNDECIDED"
else:
    → 점수가 큰 쪽
```
- 부동소수점 오차 때문에 `==` 비교는 믿을 수 없습니다. 그래서 **허용오차(epsilon) 기반**으로 비교합니다.
- UNDECIDED는 Cross/X 어느 쪽 expected와도 같지 않으므로 FAIL이 됩니다.

### 2-5. data.json 처리와 예외 정책
- 패턴 키 `size_{N}_{idx}`에서 N을 뽑아 `size_N` 필터를 고릅니다.
- 아래 경우는 **해당 케이스만 FAIL**로 처리하고 원인을 출력한 뒤 다음 케이스로 넘어갑니다. 프로그램은 중단되지 않습니다.
  - 키 형식 오류, `input`/`expected` 누락
  - 해당 크기 필터 없음
  - 패턴이 정사각형이 아님(행/열 수 불일치), 키의 N과 실제 크기 불일치
  - 알 수 없는 라벨, 숫자가 아닌 값
- 필터 묶음에 문제가 있으면 그 크기만 로드 실패로 표시하고, 그 크기의 패턴은 "필터 없음"으로 FAIL 처리됩니다.
- 파일 없음, JSON 문법 오류는 안내 메시지를 출력하고 정상 종료합니다.

### 2-6. 모드 1 입력 검증
- 한 줄의 숫자 개수가 3이 아니면 `입력 형식 오류: 각 줄에 3개의 숫자를 공백으로 구분해 입력하세요.`를 출력합니다.
- 숫자로 바꿀 수 없는 값이면 `입력 형식 오류: 숫자만 입력하세요.`를 출력합니다.
- 오류가 나면 해당 행렬(필터 A / 필터 B / 패턴)을 **처음부터 다시** 입력받습니다.

### 2-7. 성능 측정 — `measure_ms()`
- `time.perf_counter()`로 **MAC 함수 호출 구간만** 측정합니다. 입력, 출력, 파일 읽기 시간은 빠집니다.
- 크기마다 **10회 반복한 평균(ms)** 을 출력합니다.
- 측정용 입력은 패턴 생성기로 만든 N×N Cross 패턴과 X 필터입니다.

### 2-8. 보너스
- **패턴 생성기**: `make_cross(n)`, `make_x(n)`가 N×N Cross/X 패턴을 자동으로 만듭니다. 성능 분석 입력으로 재사용합니다.
- **1차원 배열 최적화**: `Matrix.flatten()`으로 길이 N² 리스트를 만들고 `mac_flat()`이 반복문 하나로 계산합니다. 성능 표에 같은 입력과 같은 반복 횟수로 2D와 1D 결과를 나란히 출력합니다.

## 4. 결과 리포트

### 4-1. FAIL 케이스 원인 분석

실패 3건을 **데이터/스키마 문제 → 로직 문제 → 수치 비교 문제** 순서로 하나씩 점검했습니다.

1. **데이터/스키마 문제가 아님.** 6개 패턴 모두 키의 N과 실제 크기가 같고 정사각형이며, 필터 3종도 모두 정상 로드됐습니다. 실패 사유에 "스키마/데이터 오류"가 하나도 없습니다.
2. **라벨 문제가 아님.** expected의 `'+'`/`'x'`와 필터 키의 `'cross'`/`'x'`는 정규화되어 `Cross`/`X`로 비교됐습니다. 정규화를 하지 않았다면 판정 결과 `Cross`와 expected `'+'`가 문자열로 달라서 PASS 3건까지 **6건 모두 FAIL**이었을 것입니다.
3. **MAC 로직 문제가 아님.** 패턴 입력은 0/1로 된 깨끗한 Cross/X 모양이고, PASS 3건은 점수 차이가 8.8~52.8로 뚜렷하게 정답 쪽이 높습니다. 모드 1의 미션 예시(A=1.0, B=5.0, 판정 B)도 손으로 계산한 값과 같습니다.
4. **원인은 필터 가중치 설계로 생긴 동점 + 비교 정책입니다.** data.json의 필터는 일부러 가중치를 조정해 두었습니다.
   - `size_5`: Cross 필터 중앙 `0.9`, X 필터 전체 `0.1` → X 패턴(9칸)에서 Cross 0.9 vs X 9×0.1 = 0.9
   - `size_13`: Cross 필터 전체 `0.3`, X 필터 중앙만 `7.5` → Cross 패턴(25칸)에서 Cross 25×0.3 = 7.5 vs X 7.5
   - `size_25`: Cross 필터 중앙 `4.9`, X 필터 전체 `0.1` → X 패턴(49칸)에서 Cross 4.9 vs X 49×0.1 = 4.9
   수학적으로는 세 케이스 모두 **정확한 동점**입니다.
5. **부동소수점 오차가 실제로 발생했습니다.** `0.1`, `0.3`, `0.9`는 2진수로 정확히 표현되지 않습니다. 그래서 반복 누적한 결과가 `0.8999999999999999`, `7.499999999999997`, `4.899999999999999`처럼 수학적 값에서 1e-15 수준으로 벗어났습니다.
6. 만약 `==`나 단순 `>`로 비교했다면 이 오차 때문에 동점이 우연히 한쪽으로 판정됩니다. 예를 들어 size_5_1은 0.9 > 0.8999…이므로 **Cross로 오판(FAIL)**, size_13_2는 7.5 > 7.4999…이므로 **X로 오판(FAIL)** 됩니다. 결과는 같은 FAIL이지만 이유가 "근거 없는 판정"이 되고, 더하는 순서만 바꿔도 결과가 뒤집힐 수 있습니다.
7. epsilon(1e-9) 비교를 적용하면 1e-15 수준의 차이는 **동점(UNDECIDED)으로 일관되게** 처리됩니다. 따라서 이 FAIL 3건은 버그가 아닙니다. 비교 정책이 의도대로 "판정할 근거가 없다"고 보고한 결과입니다.
8. 참고로, 사전 분석 때 Python 내장 `sum()`으로 계산하면 오차가 0으로 나왔습니다. Python 3.12부터 `sum()`이 보정 합산(Neumaier)을 쓰기 때문입니다. 같은 데이터라도 **합산 방식에 따라 결과가 달라질 수 있다**는 점이 epsilon 정책이 필요한 또 하나의 근거입니다.
9. 이 FAIL을 없애려면 코드가 아니라 **데이터를 고쳐야** 합니다. 필터 가중치를 동점이 나지 않게 조정하거나, expected를 UNDECIDED로 허용하는 스키마로 바꾸면 됩니다. 판정 로직을 동점일 때 expected에 맞추도록 바꾸는 것은 결과를 조작하는 것이므로 하지 않았습니다.

**의도적 오류 입력 검증.** data.json 복사본을 일부러 망가뜨려 실행했고, 4가지 모두 해당 케이스만 FAIL 처리되고 프로그램은 끝까지 진행됐습니다.

| 조작 | 출력된 실패 사유 |
|---|---|
| size_5_1 행 1개 삭제(4×5) | 스키마/데이터 오류 - 1번째 행의 열 수 5 != 행 수 4 |
| size_13_1에 5×5 패턴 넣기 | 스키마/데이터 오류 - 크기 불일치: 키는 13×13, 패턴은 5×5 |
| size_7_1 추가(필터 없음) | 스키마/데이터 오류 - size_7 필터 없음 |
| size_5_2 expected를 `'o'`로 변경 | 스키마/데이터 오류 - 알 수 없는 라벨: 'o' |

### 4-2. 시간 복잡도 분석 — O(N²)

1. MAC 연산은 N×N 칸을 한 번씩 방문하며 곱셈 1회와 덧셈 1회를 합니다. 따라서 연산 횟수는 정확히 **N²** 이고, 시간 복잡도는 **O(N²)** 입니다. 메모리는 누적 변수 하나라서 추가 공간은 O(1)입니다.
2. 연산 횟수는 9 → 25 → 169 → 625로 늘어납니다. 3×3 대비 25×25는 **약 69배**입니다.
3. 측정 시간은 0.0011 → 0.0030 → 0.0128 → 0.0450 ms로, 3×3 대비 25×25가 **약 41배**입니다.
4. 큰 크기끼리 비교하면 비례 관계가 더 분명합니다. 13×13 → 25×25에서 연산 횟수는 3.7배, 시간은 약 3.5배로 거의 같은 비율로 늘었습니다.
5. 작은 크기에서 비율이 덜 맞는 이유는 **고정 비용** 때문입니다. 함수 호출, 루프 준비, `perf_counter()` 호출 같은 비용은 N과 상관없이 들어갑니다. 그래서 연산 1회당 시간이 3×3에서는 약 122 ns, 25×25에서는 약 72 ns로 작은 크기일수록 커 보입니다. N이 커질수록 고정 비용 비중이 줄어 시간이 N²에 수렴합니다.
6. 즉 측정 결과는 "시간 ≈ 고정 비용 + c·N²" 형태로 설명되고, N이 클 때 지배하는 항은 N²입니다.
7. N이 2배가 되면 연산량은 4배가 됩니다. 실제 AI 모델은 수백×수백 필터를 수천 개 쓰므로 직렬 반복문으로는 감당하기 어렵습니다. 그래서 MAC을 동시에 수천 개 처리하는 **NPU(병렬 처리)** 가 필요합니다.
8. **보너스(1D 최적화) 비교**: 같은 입력과 같은 반복 횟수에서 1D 방식이 25×25 기준 약 2.8배 빨랐습니다(0.0450 → 0.0163 ms). 복잡도는 똑같이 O(N²)입니다. 차이는 `get(i, j)` 메서드 호출과 이중 인덱싱이 사라져 **연산 1회당 상수 비용(c)** 이 줄어든 데서 나옵니다. 알고리즘 복잡도와 상수 최적화는 다른 문제라는 점을 확인했습니다.
